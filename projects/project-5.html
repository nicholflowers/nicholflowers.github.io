NLP GenAI LLM Retrieval

RAG System Design & Evaluation

A retrieval-augmented generation system built to answer technical questions from a corpus of ArXiv papers, Wikipedia articles, and NLP blogs, with tailored responses for two very different audiences.

Problem

A tech company wanted to use GenAI to help internal teams stay current on NLP research. Two personas needed answers from the same corpus: engineers who wanted technical depth and marketing staff who needed accessible summaries. The system had to retrieve the right context and generate answers that matched the audience, not just the question.

The corpus included 18+ ArXiv papers, Wikipedia articles on generative AI, and blog posts covering open-domain QA, prompt engineering, and attention mechanisms.

Approach

I tested chunk sizes from 128 to 768 tokens and landed on 448-512 with 50-64 overlap. Smaller chunks fragmented technical explanations; larger ones diluted precision. I chose multi-qa-mpnet-base-dot-v1 as the embedding model after testing five sentence-transformer variants, and stored embeddings in Qdrant.

Initial retrieval with small k values (8-10) wasn't consistently surfacing the best matches. I pushed k to 30 and added a Cohere reranker, which caught relevance that cosine similarity missed. A soft deduplication step (0.9 cosine threshold) filtered near-duplicate chunks before generation.

Both personas received the same retrieved context but different system prompts. The engineering prompt required technically grounded, source-traceable responses. The marketing prompt required accessible, jargon-free summaries. Early marketing prompt versions still produced research-abstract-style responses, requiring iteration to get right.

I evaluated using LLM-as-a-Judge (Groq/Llama3-70b scoring against gold answers on a 1-5 scale) and RAGAS context precision (measuring retrieval relevance separately from generation quality). The combination let me diagnose whether a bad answer came from bad context or bad generation. The test set included out-of-domain questions to verify the system would decline rather than hallucinate.

Parameters iterated on: chunk size (128-768), overlap (0-96), retriever k (8-30), five embedding models, Cohere reranking, soft dedup, and two LLMs (Mistral-7B quantized vs. Cohere). Each configuration was batch-evaluated with async processing and retry logic to handle token and rate limits.

Results

The final configuration achieved strong LLM-as-a-Judge scores (4-5 out of 5) on engineering and marketing responses across the validation set. Key findings from experimentation:

  • Chunking was the highest-leverage decision. Chunk size affected answer quality more than which LLM generated the response.
  • Reranking outperformed retriever tuning. Pulling back 30 documents and reranking beat trying to get the retriever to return only the best 8.
  • Separating retrieval and generation evaluation was critical. A good final answer could mask bad retrieval, and measuring both independently pointed to different fixes.
  • Token economics shaped the architecture. Full evaluation suites exhausted API limits, forcing batch processing, retries, and prioritization of which metrics to run when tokens ran low.
